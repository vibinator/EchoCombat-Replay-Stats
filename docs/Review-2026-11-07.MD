## Bugs (ordered by impact)
- **BUG-1 — `database is locked` at startup loses work.** Several threads write SQLite at once (worker results, combat ingest,
  arena poll, scanner, duplicates refresh); the connection uses Python's default 5 s busy timeout. First start of the review: 9
  lock errors in 30 s → `Saving replay 48204 failed` (row stuck `processing` until the next restart), 3 combat reports saved
  as `failed: Save failed: database is locked` (never retried until the file changes or `COMBAT_VERSION` bumps), the arena
  poll failed once. Second start: 1 error. On the NAS (slower disk, 2 workers) this will happen at every start.
  *Where:* `backend/db.py: open_db`, `worker.py: save_result`, `combat.py: _process`, `arena.py` (`todo` block).
  *Options:* (a) `create_engine(..., connect_args={"timeout": 30})` + `PRAGMA busy_timeout=30000` (one line, removes nearly all
  of it); (b) on `OperationalError` in `save_result` set the row back to `queued` instead of leaving it `processing`, and let
  combat `_process` keep the row `queued` so it is retried next cycle; (c) longer term, one writer thread with a queue
  (the Architecture doc still says "one writer" but that stopped being true with combat / arena / console / profiles).
- **BUG-2 — Replay root change duplicates the whole archive.** `replays.source_path` is relative to `ECHOVR_REPLAY_SOURCE`.
  The local setting moved from `…\Replays` to `e:\ECRanked` on 2026-11-03, so every file was discovered again under
  `Replays/…` (29.9k new rows beside the 29.4k old ones; 59.5k rows for 29.7k files). The old rows have no file any more:
  their matches still show, their 3D playback answers 404 (`no_tracks3d`, the file cannot be read), and because
  STATS_VERSION changed they are queued for a re-read that fails as `unreadable` (≈ 28.7k rows: the previous match is
  kept with a warning, so no deletion, but the rows never get the new stats and sit in the queue every restart). Also picked up:
  `EchoRecorder/dist/<guid>/<guid>.echoreplay` (recorder test output). **Fixed 2026.11.07.2:** Console > Replays > "Forget
  replays whose file is gone" / `admin.bat forget-missing`; for this PC also set `ECHOVR_REPLAY_SOURCE=E:\ECRanked\Replays` and
  `ECHOVR_COMBAT_SOURCE=E:\ECRanked` in `settings.local.bat` first (otherwise the `Replays/…` rows are the ones that stay).
  *Options:* (a) set `ECHOVR_REPLAY_SOURCE=E:\ECRanked\Replays` and `ECHOVR_COMBAT_SOURCE=E:\ECRanked` in `settings.local.bat`, then
  an admin command `forget-missing` (new) that deletes `replays` rows (and matches) whose file is gone — or delete the local
  database and re-import (3 h); (b) make the scanner key files by a stable id (`session_id` from the file name / size + mtime) so
  a moved root re-links rows instead of duplicating them; (c) at least warn in the Console when > 10 % of `done` rows point to
  missing files, and let the worker mark `unreadable` rows without deleting the existing match (today a failed re-read removes it).
- **BUG-3 — Combat report save failures are permanent.** `combat._process` writes `failed: Save failed: …` and only retries
  when the file's size / mtime changes. Transient errors (BUG-1) therefore lose reports. *Option:* keep the row `queued` on
  non-parse errors; show "retrying" in the Console.
- **BUG-4 — `GET /api/matches/<30 digits>` → 500.** `OverflowError: Python int too large to convert to SQLite INTEGER`
  (`int` path params are unbounded). Harmless but logs a traceback and bypasses the error format. *Option:* `Path(le=2**62)`
  on match / replay ids or a global `OverflowError → 404` handler in `errors.py`.
- **BUG-5 — Flaky remote-worker test is a real race.** `Worker._claim` reads the remote mode, then claims; the test switches
  remote mode on between those two steps, so the in-process worker thread takes the replay the test wanted to claim
  (`IndexError: list index out of range`) or the stale `pc_on=False` requeues the PC's claim. *Options:* re-check the mode
  inside `claim_queued` (same transaction), or in the tests call `worker.wait_idle()` after `switch()` before `scan_once`.
- **BUG-6 — `?tab=` with an unknown value renders an empty match page** (`MatchPage.tsx: tab = params.get("tab") || "players"`).
  `/matches/123?tab=3d` (or an old link to a removed tab) shows the header and nothing below. *Option:* fall back to
  `players` when the value is not in `TABS`.
- **BUG-7 — Match page asks `/api/combat/matches/<session>` for every match and logs a 404** when there is no combat report
  (every match before 2026-11-04). Console noise and a wasted request per match view. *Option:* 200 with `{found: false}` /
  204, or only ask when `match.has_combat` (one boolean on the match answer).
- **BUG-8 — `config.py:100` has an invalid escape sequence** (`"\E"` in a docstring: SyntaxWarning under `-W error`; Python 3.14 makes it louder). One `r"…"`.
- **BUG-9 — Validation errors are not in the site's error format.** FastAPI 422s return `{"detail": [...]}`; `api.ts: errorMessage()`
  then shows "Request failed (422)". *Option:* a `RequestValidationError` handler producing `{error_code: "bad_request", message}`.
- **BUG-10 — Heatmap docs drift.** Architecture / DataModel say `cell` 0.25 / 0.5 / 1; the code allows 0.1 only (`heatmaps.CELL_SIZES`). Fix the docs or re-allow the coarser cells (cheaper answers for phones).

## Security (nothing exploitable found; hardening options)
- **SEC-1 — Good:** signed sessions with HMAC + `compare_digest`, OAuth state cookie, `next=` restricted to site paths (checked:
  `https://evil.example` and `//evil.example` both land on `/achievements`), bearer secrets compared in constant time, PNG
  upload validated by magic + size + hash name, custom icon names regex-locked, static traversal refused, read-only middleware,
  CSP / COOP / nosniff / referrer headers present, `/docs` `/openapi.json` hidden, replay file paths refused, pickle restricted
  to a class whitelist for the remote worker, rate limiter proven (130 burst → 429 with `Retry-After`).
- **SEC-2 — `ECHOVR_DISCORD_PREVIEW_ROLES` gives the Console to any 17–20-digit id** and the login is "on" with *any* non-placeholder
  secret + token. That is exactly how this review bypassed Discord; it needs server env access, so it is not remote-exploitable,
  but a wrong/typo'd id in the YAML silently grants staff rights to a stranger. *Option:* at startup, resolve the ids via the bot
  and log a warning for ids that are neither a role nor a member of the server; show the same on the Permissions page.
- **SEC-3 — Staff can see raw SQL / driver errors.** The Console "Arena counter" card prints the full `OperationalError` text
  including the `INSERT INTO nakama_accounts (...)` statement. *Option:* keep the first line only (`arena.py` status text).
- **SEC-4 — Body validation runs before the secret check** on `/api/bot/*` and `/api/worker/*` (an unauthenticated caller
  gets 422 with the expected field names). Cosmetic; *option:* a dependency that checks the bearer first.
- **SEC-5 — Twitch embed loads third-party trackers on the home page** (`amazon-adsystem`, `live-video.net` stats) for every
  visitor, and the CSP allows `frame-src https://player.twitch.tv`. *Options:* click-to-load (poster image + "Watch" button) or a
  `parent=` embed only while live; mention in a privacy line in the footer.
- **SEC-6 — Session key and data folder** are plain files (`data/session.key` 0644). Fine on the NAS volume; document that
  deleting it logs everyone out (it is documented) and keep it out of backups shared with others.
- **SEC-7 — No dependency audit in CI.** `pip` / `npm` versions are pinned (good) but nothing checks advisories. *Option:*
  `pip-audit` + `npm audit --omit=dev` steps in `docker-image.yml` (non-blocking at first).
- **SEC-8 — Rate limiter keys on IP only.** Behind Cloudflare that is per visitor; on the home network everyone behind the same
  NAT shares a bucket. Acceptable; noted.

## Performance (measured on this PC, 4 import workers running)
| Request | Cold | Warm / cached |
|---|---|---|
| `/api/overview` | 40 ms | 2 ms (HIT) / 304 |
| `/api/leaderboard` (all time, games) | 380 ms | 10 ms |
| `/api/matches?player_name=a` | 200 ms | — (LIKE scan over 222k rows) |
| Player heatmap, busiest player, `last=5000` (2.2k matches) | 6.7 s, 4.2 MB | 14 ms |
| Player achievements, busiest player (8.7k games) | 5.6 s | 20 ms (per data stamp; per visitor header) |
| Console `status` command | 60 ms – 7 s (under import load) | — |
| Match heatmap / playback / playback3d | 37 / 10 / 34 ms | — |
| 40 parallel page requests | max 190 ms, median 80 ms | — |
| Players page (browser, networkidle) | 14 s | the avatar lookups (Discord) hold `networkidle`; the page itself paints in < 1 s |

*Options:*
- **PERF-1** Busy-timeout + single writer (BUG-1) also removes the write stalls that make `status` take 7 s.
- **PERF-2** Player achievements for heavy players: cache the per-player `Game` list per data stamp (the 5.6 s is mostly
  rebuilding 8.7k `Game` objects), or compute the medal ladder incrementally per new match.
- **PERF-3** `player_name` filter: a `players.name COLLATE NOCASE` index or an FTS5 table for name search (also `/api/search`).
- **PERF-4** Heatmap payloads: 4–8 MB JSON for `last=5000`; a `uint16` binary body (or `cell=0.25` for phones) would cut it 4×. Memory
  note: `tracks.read` LRU is 512 MB by default — fine on the PC, check on the NAS.
- **PERF-5** The home page waits for Twitch; render the embed after first paint (it is below the fold on phones).
- **PERF-6** `/api/avatars` fan-out: one request per page with up to 50 ids → 0.6 s even when Discord says 401; cache negative
  answers for the budget window (it does for positive ones).
- **PERF-7** Import: 200 replays/min at 4 workers here; the 29k-row re-read after a STATS_VERSION bump is the main CPU cost of a
  release. The IN_PLACE_COLUMNS pattern (D57) avoids the rebuild; consider making "stats version bumps re-read only matches
  newer than X" an admin choice for the NAS.

## Data quality (local database, 31.7k matches)
- **DATA-1** Duplicated archive rows after the root change (BUG-2) — the biggest issue for the local copy.
- **DATA-2** `winner` is NULL for 6.4k of 16.1k capture-point and 7.1k of 15.6k payload matches (early replays lack the data,
  and short / abandoned matches). Fine, but the home "capture point wins" and leaderboard win rates silently exclude 43 %.
  *Option:* show "decided matches: N" beside win-rate figures (the payload card does, the capture one does not).
- **DATA-3** 915 matches shorter than 60 s and 7.1k with fewer than 6 players are in every aggregate (win rate, speed, deaths).
  Achievements already require 4+ min / 3+ per team; profiles and leaderboards do not. *Option:* a global "counted match" rule
  (≥ 2 min, ≥ 2 per team) applied in one place (`duplicates.counted`-style predicate) with the totals still shown.
- **DATA-4** 7.5k `match_players` rows have `frames_in_bounds = 0` (spectators / people who never left spawn): their % stats are
  undefined and `deaths_est` 0 drags averages. *Option:* exclude from per-player averages, count as "watched".
- **DATA-5** `ping_frames = 0` for 247 rows and 131 rows average above 500 ms — the 999 exclusion (D24) leaves real spikes in.
  *Option:* cap at 400 ms for averages, keep raw in the match page.
- **DATA-6** 427 matches with a frame rate < 5 or > 40 Hz (recorder hiccups). Speeds from those are noisy; flag the match ("low
  recording rate") instead of trusting its top speed (the top-speed record holder is 45.9 m/s; the next is far below).
- **DATA-7** Names: 194 case-insensitive duplicate names across different ids (merge candidates, the Console lists them),
  12 names with `<`/`>` (fine, rendered as text), one player with 48 name changes. User ids vary from 2 to 19 digits: 1.1k
  short ids (≤ 5 digits) are old-platform ids, not Discord ids — `is_discord_id` already handles that.
- **DATA-8** `events` is the largest table (4.7 M rows, 1.67 M `death_est` + 1.64 M `respawn`); only the timeline uses it. Option:
  keep deaths / respawns in the tracks file instead and drop them from SQL (≈ 60 % of the table), or add `(match_id, type)` index.
- **DATA-9** `frames_lone_wolf_near` is NULL for 218k rows until the re-read finishes — the Lone Wolf achievement is under-counted
  meanwhile. The Console could say "N matches not yet re-read for <rule>".
- **DATA-10** Combat `nakama_accounts`: 69 accounts, 14 linked to replay players (20 %); linking by Discord id only works for
  players whose replay id *is* their Discord id (newer recordings). A name-match suggestion list in the Console would lift this.
